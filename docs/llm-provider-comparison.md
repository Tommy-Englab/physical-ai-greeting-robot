# LLMプロバイダー比較（Task 0）

> B案（自然言語→LLM→安全なプリセットJSON計画）のためのLLM選定メモ。確認日: 2026-10-11。最新APIは実装直前に公式ドキュメントで再確認する。

## 結論（確定: Gemini 採用、2026-10-11）

**採用プロバイダー: Google Gemini（Gemini Developer API、無料枠）。** gemini-flash 系モデルを想定。

採用理由:
- **無料で使える**（決定打）。Google AI Studio でAPIキーを発行すれば、課金設定（billing）を有効にしなくても対象モデル（gemini-flash系）へ無料でリクエストできる。本案は「短い自然言語→小さなJSON」で1回数百〜数千トークンと軽く、無料枠のレート制限内で足りる。合格優先・低コストの方針に最適。
- JSONスキーマ準拠の構造化出力をPythonで正式サポート（google-genai SDK）。B案の安全設計（validator前段）と相性が良い。
- 対して OpenAI は、無料枠の有効化にも支払い方法の登録が必要で、旧来の無料クレジットは廃止済み（最低$5購入から）。コストをかけない方針に合わない。

確認日 2026-10-11（料金・無料枠は変わりやすいため、実装直前に公式ページで再確認する）。

> 注意: 無料枠は利用規約の範囲で使う。本案が送るのは「お辞儀して」等の自然言語指示のみで、個人情報・秘密を含まない。
> APIキーはユーザーが Google AI Studio で発行し、`.secrets/` または環境変数で管理する（チャット・コード・commitへ貼らない）。

OpenAI・Gemini とも、本案に必須の「JSONスキーマ準拠の構造化出力」をPythonで正式サポートしており技術的にはどちらでも成立する。その上で、上記のとおり無料で使える Gemini を採用した。

## 本案にとって重要な事実

- 我々の用途は「短い自然言語指示 → 少数のプリセット選択・順序・回数のJSON」。入出力トークンは小さく、最安モデルで足りる。コストは軽微な見込み（1回の指示で数百〜数千トークン程度）。
- 両者ともJSON Schemaで出力形式を強制できるため、「LLMが生の関節角や余計な説明文を出す」リスクをスキーマ側で抑えられる。これは本案の安全設計（validator前段）と相性が良い。
- どちらを選んでも、設計（validator・プリセット実行・ROS2変換）は共通化できる。プロバイダー差はクライアント呼び出し部分に局所化する。

## 実測ログと申し送り（2026-10-12、Task 1 接続確認）

次セッションへの引き継ぎ。無料枠が「使えないのでは」と毎回誤認しやすいので、切り分け結果を残す。

### 結論: 無料枠は使える。503はGoogle側の一時的高負荷でキー起因ではない

Mac上の一時venv（google-genai 2.30.0 / pydantic 2.14.1）とcurlで実測した事実:

- **キーは有効**。モデル一覧API（`GET /v1beta/models`）が **HTTP 200** を返す。無効キー・課金未設定なら401/403になるが、200＝無料枠で正常に認証できている。
- **推論も成功実績あり**。`gemini-flash-latest` へ `generateContent` をcurlで投げたら **HTTP 200・`"text":"pong"`** を取得。無料枠で推論1回成功を確認済み。
- その後、同じモデルで断続的に **503 UNAVAILABLE「high demand（高負荷）」** が複数モデルで発生。これは429(レート超過)ですらなく、純粋なGoogle側のサーバー高負荷。**こちらのコード・キー・課金では解決できない。時間を置くしかない。**
- 誤認注意: curlの `-w '%{http_code}'` で404に見える場合でも、本文は503のことがある。本文(`error.message`)を必ず確認する。「503=混雑」であって「使えない」ではない。

### 使えるモデルID（実測）

- `gemini-flash-latest`: 存在・無料で疎通確認済み（推論200実績）。ただし高需要エイリアスで503が出やすい。
- `gemini-3.8-flash`: 存在・スキーマ受理OK（404/400は出ず、503のみ）。公式が `gemini-2.5-flash` の移行先として案内。
- `gemini-2.5-flash`: **新規ユーザーには提供終了（404）**。使わない。移行先は `gemini-3.8-flash`。
- モデルIDは `GEMINI_MODEL` 環境変数でスクリプトに渡せる。混雑時はエイリアスでなく具体バージョン（例 `gemini-3.8-flash`）を試す。

### 構造化出力スキーマの重要な修正（本番コードに効く）

- Geminiの `response_schema` は **`additionalProperties`（Pydanticの `extra:"forbid"` が出力する）を受け付けず 400 INVALID_ARGUMENT** になる。
- 対処: Geminiへ渡す**送信用スキーマには `extra:"forbid"` を付けない**。未知フィールド拒否は**受信後のローカル検証モデル側で担保**する（二重防御。design 2.2「LLM出力は信頼せず検証」と整合）。
- `experiments/task1_connection/gemini_connection_check.py` は送信用(`PlanOut`)と受信検証用(`Plan`)を分けて実装済み。

### 方針（ユーザー判断・2026-10-12）

- 503のリスクを承知の上で、Geminiの無料枠を使い続ける。合格優先のため有料化はしない。
- デモ・録画・再現性試験のときは、503で失敗し得る前提で、時間に余裕を持って実行する。混雑時はモデルIDを変える、間を置いて再試行する。
- どうしても当日通らない場合に備え、保存計画の `saved` モード再生（AC-6・加点枠）が最後の保険になる。

## 無料枠レート制限の実測（2026-10-13、Task 3 検証中に判明。重要）

Google AI Studio のレート制限ダッシュボードで、`gemini-flash-latest`（実体表示は **Gemini 3.8 Flash**）無料枠の制限値を実測した。

| 指標 | 無料枠の制限 | 備考 |
|---|---|---|
| **RPM**（1分あたりリクエスト） | **5** | 連続実行で即到達する。テスト・デモは1分5回まで |
| TPM（1分あたり入力トークン） | 250K | 本案は1回数百〜数千トークンで全く問題にならない |
| **RPD**（1日あたりリクエスト） | **20** | **1日の総リクエストがわずか20回**。これが最大の制約 |

### 429 RESOURCE_EXHAUSTED の実測

- Task 3 の感情解釈テスト（連続5指示）＋範囲設計テストを続けざまに叩いたところ、`429 RESOURCE_EXHAUSTED`（quota超過）が発生。
- **原因は 503（Google側高負荷）ではなく 429（こちらの無料枠レート超過）**。RPM=5 に到達、かつ RPD も 17/20 まで消費していた。
- 切り分け: 低レベルで例外本文を確認し `429 RESOURCE_EXHAUSTED` と判明（キー・課金・実装の問題ではなく、使用頻度の問題）。

### 設計・運用への影響（重要）

1. **1日20回の制約は本番運用に直結する。** 動画撮影でlive推論を何度もやり直すと、その日のうちに使い切る。録画はRPDに余裕のある日の早い時間に、投げる指示を事前に確定して最小回数で行う。
2. **`saved` モード（AC-6・加点枠）の意義が決定的になった。** 本番でRPDを使い切ったら live が一切叩けない。検証済み canonical JSON を再生する saved モードが現実的な保険。動画・レポートには `live` / `saved` を明記する（自動で成功扱いにしない）。
3. **テストは live を極力使わない。** validator（schema/意味/範囲検査）は Gemini 非使用で単体テスト可能。「LLMがこう返したらどうなるか」はフェイクで検証し、live消費を温存する。
4. 混雑時の 503 と枠超過の 429 は別物。503＝時間を置く／モデルID変更。429＝その分（RPMなら1分、RPDなら翌日 UTC-8 リセット）まで待つしかない。
