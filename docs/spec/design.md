# 設計（design）

## 1. 設計方針

講座サンプル「ChatGPT API自然言語操作」（出典: `docs/course-materials/最終課題要件_2026-10-08版.md` の最終課題サンプル）をベースラインとして調査する。ただし丸写しせず、LLMを**許可済み動作の計画者**に限定し、ロボット制御値を生成する権限を与えない。

目的は講座合格であり、自然言語から複数の安全確認済み動作を組み合わせて実行する最小構成を優先する。教師データ収集、ACT学習、peg-in-holeは現行設計に含めない。旧設計は `.kiro/specs/_backup/final-project-act-peg-in-hole-pre-llm/` を参照する。

### 合格必須と加点の区別（requirements 6節に対応）

本設計は、合格必須（Must: AC-1,2,3,7）を成立させる部分と、加点・堅牢化（Should: AC-4,5,6）の部分を含む。両者は役割が違う。

- 合格必須の設計は必ず全部実装する。これが揃えば合格ラインに到達する。
- 加点・堅牢化の設計（安全境界=AC-4、再現性=AC-5、フォールバック=AC-6）は、合格には不要だが、後から足せない設計事項（データフローへの組み込み、固定推論設定、正規化等）であるため、設計としては最初から見込んでおく。ただし作り込みの深さは余力に応じて調整し、締切が厳しければ最小限で止める。該当セクションに「【加点・余力枠】」と明記する。

## 2. 論理設計（技術非依存）

### 2.1 責務とデータフロー

```text
[ユーザーの自然言語]
        ↓
[計画生成AI] 許可済み動作だけで構造化計画を生成
        ↓
[構文・安全Validator] 不正・危険なら実行せず停止
        ↓
[プリセット実行器] 計画順に安全確認済み軌道を選択
        ↓
[ロボット制御変換]
        ↓
[シミュレーション上のCRANE+ V2]
```

- 計画生成AIは「何を、どの順で、何回行うか」を決める。
- Validatorは計画を信頼せず、許可リスト、型、回数、全体長、未知フィールドを検査する。
- プリセット実行器だけがロボット固有の関節軌道を保持する。
- 制御変換層は検証済みプリセットをロボット向けメッセージへ変換する。

### 2.2 信頼境界（AC-4対応・工夫点。設計必須／作り込みは加点枠）

> この信頼境界と安全停止はAC-4（加点・工夫点）に対応する。合格必須ではないが、B案のデータフロー（検証を通ってから送る）に最初から組み込む前提で設計する。基本的な許可リスト・型・上限の検査は低コストで成立するためまず入れ、網羅的な異常系の作り込み（Task 4相当）は余力枠とする。

LLM出力は常に外部入力として扱う。次の境界を越えさせない。

| LLMに許可する | LLMに許可しない |
|---|---|
| `bow` / `rotate_base` / `wave` の選択 | 生の関節名・関節角・速度・加速度・トピック名の生成 |
| 実行順序 | 任意コード・シェル・ROS 2コマンドの生成 |
| schemaで許可した方向・回数 | schema外フィールド、無制限の回数・時間 |

MVPの計画例:

```json
{
  "version": "1.0",
  "actions": [
    {"preset": "rotate_base", "parameters": {"direction": "right"}},
    {"preset": "bow", "parameters": {"repetitions": 1}}
  ]
}
```

この例はインターフェース案であり、正式schemaはプロバイダー比較後に固定する。`additionalProperties: false` 相当を全階層に適用し、`joint_angles` 等の追加は拒否する。

### 2.3 状態遷移と停止

```text
IDLE → PLANNING → VALIDATING → READY → EXECUTING → COMPLETED
          │             │          │          │
          └─────────────┴──────────┴──────────┴→ STOPPED
```

- `VALIDATING` 合格前にロボットへ送信しない。
- APIエラー、不正JSON、schema違反、許可外動作、内部プリセットの可動範囲違反、タイムアウト、ユーザー停止は`STOPPED`へ遷移する。
- `STOPPED`では未送信の後続アクションを破棄し、新規軌道を送らない。コントローラ固有の安全停止方法は1動作E2E前にGazeboで検証して確定する。
- 一部実行後の自動再開はしない。再実行には新しい明示操作を必要とする。

### 2.4 再現性（AC-5対応・【加点・余力枠】）

> 再現性（同一指示を3回実行して一致）はAC-5（加点・堅牢化）に対応し、合格必須ではない。ただし固定推論設定・JSON正規化は後から足しにくいため、設計方針は最初から見込む。3回試験（Task 5相当）の実施自体は合格ライン到達後の余力枠とする。

- プロバイダーが提供する固定可能な推論設定と構造化出力を使用する。
- JSONをschema適用後に、キー順、既定値、方向、回数を正規化してcanonical JSONを作る。
- 同一指示の3回試験では、リアルタイムLLM推論のcanonical JSONと、実行したプリセット順・方向・回数を比較する。
- 揺れが残る場合はプロンプトとschemaを狭める。保存計画再生でAC-5を代替しない。

## 3. 技術構成（技術固有）

### 3.1 実行環境

- 講座公式Dockerイメージ: `airobotbook/ros2-desktop-ai-robot-book-humble:latest`
- コンテナ: `pai_ros2`
- ROS 2 Humble / Gazebo Sim 6 / CRANE+ V2
- GUI: `http://localhost:6080/`
- ROS 2通信を使うシェルでは、`/opt/ros/humble/setup.bash`、`~/airobot_ws/install/setup.bash`、`~/pai_ws/install/setup.bash` をsourceする。

クラウドのロボットリソースは作らない。将来作成するROS 2パッケージ名、ノード名、設定ファイル名は実装前に確定する。

### 3.2 コンポーネント

| コンポーネント | 責務 | 主な入出力 |
|---|---|---|
| Input CLI（第一候補、未確定） | 自然言語と実行モードを受け付ける | text / live・saved |
| LLM client | プロンプト送信とJSON応答取得 | text → untrusted JSON |
| Plan parser / validator | parse、schema、安全上限、正規化 | untrusted JSON → validated plan |
| Preset registry | 許可済み軌道とメタデータを保持 | preset名 → 関節軌道 |
| Plan executor | 順序制御、タイムアウト、停止 | validated plan → preset実行 |
| Trajectory publisher | ROS 2形式へ変換・送信 | preset → `JointTrajectory` |
| Audit logger | 計画・検証・実行結果を秘密なしで記録 | イベント → ログ |

ROS 2への最終出力は、CRANE+ V2の既存コントローラが受け付ける `trajectory_msgs/msg/JointTrajectory` とする。実際のトピック名、関節順、QoS、action/topicの選択は既存launchと実行中のinterfaceを確認して固定する。

### 3.3 プリセット設計

MVPの外部名は次の6種類に固定する（テーマ「あいさつコミュニケーションロボット」。requirements 1.1/2 参照）。各動作は異なる関節を主役にして見分けられるようにした（2026-10-18 Gazebo目視で確定）。

- `bow`: 肩(joint2)前傾でお辞儀し、開始姿勢へ戻る。`repetitions`（1..5）可。
- `nod`: 肩(joint2)を浅く速く動かしてうなずく。`repetitions`（1..5）可。
- `cheer`: 肘(joint3)を跳ね上げて腕を上げる（喜び・万歳）。`repetitions`（1..5）可。
- `wave`: 肘(joint3)を少し曲げ手首(joint4)を左右に振る。`repetitions`（1..5）可。
- `rotate_base`: 基部(joint1)で左右を向く。`direction` は `left` / `right` のみ。LLMから角度を受け取らず、方向別の固定角を使う。
- `grip`: グリッパ(joint_hand)を開閉する。gripperコントローラ宛て。`repetitions`（1..5）可。

旧 `look_up`（joint2後傾）は bow と同軸で見分けにくいため廃止し、`cheer`（joint3）・`grip` を追加した。LLMは動作名の直接指定だけでなく、あいさつ語・感情表現の意図を上記プリセットの選択・順序・回数へ翻訳する（例「こんにちは」→bow、「うれしい！」→cheer→wave）。個々の動作の意味より、組み合わせ・系列で感情の総体を作る。翻訳の指針はシステムプロンプトに例示するが、出力は常に6プリセット・許可パラメータの範囲に制約し、検証で逸脱を拒否する。対応表は `docs/preset-and-schema-design.md` 5節、理論的裏付けは `docs/report-draft.md` 11節。

各プリセット定義は、開始姿勢、関節名と順序、waypoint、各区間時間、想定総時間、終了姿勢を持つ。正式な角度、速度相当の時間、回数上限、連結可能条件は、CRANE+ V2のURDF・コントローラ制限とGazebo目視を照合してから設定する。起動時またはテスト時にも全waypointが可動範囲内であることを検査する。

> Task 0 設計済み: 関節可動範囲（公式URDF根拠）、3プリセットの軌道設計案、ニュートラル開始・終了姿勢、区間時間は `docs/preset-and-schema-design.md` に確定。全プリセットは共通ニュートラル姿勢で開始・終了し連結を安全化する。waypointの具体値はTask 2のGazebo目視で最終固定する（可動範囲内であることは設計ノートで保証済み）。関節名の順序はTask 2で `/joint_states` を実機確認してから固定する。

### 3.4 検証順序

1. 応答サイズ上限を確認する。
2. JSONとしてparseする。前後の説明文やMarkdown fenceを許容しない。
3. schemaでversion、必須項目、型、列挙値、配列長、回数、未知フィールドを検査する。
4. プリセット許可リストとプリセット別パラメータを検査する。
5. 各プリセット定義の関節範囲、連結条件、見積時間を検査する。
6. 計画全体のアクション数と見積時間上限を検査する。
7. canonical JSONを生成し、実行前に表示する。

どこか1段でも失敗した場合は実行器を呼ばない。API接続とGazebo実行の実測値はTask 1〜3で検証し、必要な場合は実装を進める前に設計値を更新する。

> Task 0 設計済み: スキーマ構造（`version`＋`actions`配列、プリセット別の許可パラメータ、`additionalProperties: false`相当）と上限値（actions配列長5／repetitions各3／見積総時間30s／応答サイズ2KB）は `docs/preset-and-schema-design.md` に確定。schema・設定・テスト期待値はこの値に一致させる。

### 3.5 APIプロバイダー選定と接続ゲート

プロバイダー、モデル、API形式は未決定である。OpenAI、Gemini等について、次を各社の公式ドキュメントと講座サンプルから比較する。

- 現在利用可能なモデルと構造化JSON/schema制約
- 料金と課金設定、無料枠の有無、利用上限
- Python/ROS 2環境への導入負荷と依存関係
- タイムアウト、再試行、エラー形式、安全機能
- 利用規約と入力データの扱い

選定結果、参照URL、確認日を構成設計へ追記してから実装する。接続ゲートはコンテナ内で、(1) HTTPS接続、(2) ユーザーが環境変数等で渡したキーによる最小推論、(3) 自然言語からschema準拠JSON、の順に確認する。1〜2時間以内に通らなければ作業を止め、B案継続かバックアップ済みACT系へ戻るかを共同判断する。

### 3.6 タイムアウトとAPI障害

タイムアウト（API応答・プリセット・計画全体）は、安全停止（AC-4）と実行の健全性に関わるため合格必須側で設計する。保存計画フォールバック（`saved`モード）はAC-6に対応する加点・堅牢化で、合格には不要（下記で明示）。

- API応答、各プリセット、計画全体に独立したタイムアウトを持たせる。Task 0 設計済みの初期値（API応答15s／各プリセット想定総時間×1.5・最低8s／計画全体最大45s／再試行は計画生成中のみ最大2回）は `docs/preset-and-schema-design.md` に確定。数値は接続実測とプリセット実測後にTask 1〜3で再調整する。
- APIの自動再試行は、同一指示の重複実行を起こさない計画生成中だけに限定し、回数を設定で固定する。ロボット実行中はAPIを呼ばない。
- **【加点・余力枠（AC-6）】** 保存計画フォールバック: API障害時は自動的に保存計画へ切り替えない。ユーザーが`saved`モードを明示的に選び、同じvalidatorを通した成功済みJSONだけを再生する。この機能自体は合格必須ではなく、余力で実装する（Task 4相当）。
- `live`または`saved`のモード表示は、`saved`を実装する場合に備えてUIとログへ常時表示できるようにする。

### 3.7 秘密・ログ

- APIキーは環境変数または `.secrets/` 内の非追跡ファイルから取得する。値をコマンド引数、spec、README、テストfixtureへ書かない。
- `.gitignore` の `.secrets/`、`.env`、`*.env` を維持する。
- ログ項目はモード、指示IDまたは秘密を含まない入力、canonical plan、検証結果、プリセット開始・終了、停止理由、所要時間とする。
- Authorization header、APIキー、SDKの認証オブジェクト、個人名を含む絶対パスは出力しない。

### 3.8 録画

Gazebo標準Video Recorderで3Dシーンを録画し、`/workspace`へMP4保存する。動画は1〜3分、2倍速までとし、倍速時は明記する。入力、JSON、検証結果は秘密・個人情報を除いた別画面または編集済み表示で確認可能にする。リアルタイム推論か保存計画再生かも明示する。

## 4. テスト方針

| レベル | 検証内容 | 主担当 |
|---|---|---|
| 単体 | schema、未知preset、未知field、回数・時間上限、canonical化、preset範囲 | Kiro |
| コンポーネント | LLM client成功・timeout・認証失敗、publisher変換、停止遷移 | Kiro |
| E2E | 自然言語→live LLM→JSON→validator→1プリセット→Gazebo | Kiro＋ユーザー |
| 異常系E2E | 未対応・危険指示、不正JSON、API障害で無動作 | Kiro＋ユーザー |
| 再現性 | 同一指示をliveで3回、canonical planとGazebo結果を比較 | Kiro＋ユーザー |
| 提出確認 | 動画、README、PDF、public化、秘密・個人情報 | ユーザー＋Kiro |

各テスト結果を `requirements.md` のAC番号と対応付けて `tasks.md` に記録する。環境依存のGazebo試験は`pai_ros2`内とブラウザGUIで行う。

## 5. 役割境界

- ユーザー: APIアカウント・キー・課金可否、動作範囲の承認、Gazebo目視、最終録画、YouTube/omnicampus提出、public化承認。
- Kiro: 公式情報調査、設計、実装、テスト、README/レポート下地、秘密・個人情報点検、commit前までの差分。
- 共同: 自然言語と動作範囲、成功条件、動画構成。
