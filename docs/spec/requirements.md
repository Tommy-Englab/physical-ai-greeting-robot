# 要件定義（requirements）

## 1. 目的と根拠

東京大学 松尾・岩澤研究室「Physical AI 応用編1 2026」の最終課題を、期限内に確実に完成させて合格する。過度な独自性、新規モデル学習、複雑な物体操作は狙わない。

課題要件の正本は `docs/course-materials/最終課題要件_2026-10-08版.md` である。同文書の「最終課題サンプル（丸写し不可・発展させて工夫点を明記）」にある「ChatGPT API自然言語操作」をベースラインとして調査・引用する。サンプルをそのまま複製せず、**生の関節角をLLMに生成させない安全境界**と、**検証済みプリセットの組み合わせによる複数動作**を本作品の工夫点とする。

### 1.1 作品テーマ（確定 2026-10-13）

**「あいさつコミュニケーションロボット」— 少数の安全な動作しか持たないロボットでも、AIが人の言葉（あいさつ・感情）の意図を汲めば、意思疎通や好感度を感じさせる振る舞いになるか。**

- 問い: 動作は有限のプリセットの寄せ集めにすぎないが、その「選択・順序・回数・強さ」をAIが言葉の意図から組み立てることで、単なる機械動作が「コミュニケーションしている」ように見えるか。
- AIの役割を一段引き上げる: 動作名の直接認識（「お辞儀して」→bow）だけでなく、**あいさつ語・感情表現の解釈 → 好感度の高い動作列への翻訳**（「こんにちは」→会釈、「うれしい！」→速くうなずく＋手を振る 等）まで踏み込む。これがルールベースの分岐では書けない、AIならではの価値であり本作品の中心的な工夫点。
- 安全境界は不変: 解釈が高度化しても、AIが出すのはプリセットの選択・順序・回数・方向だけ。関節角・速度は人間が検証した固定値のまま。「賢く振る舞うが暴走しない」ことを両立させる。

## 2. 現行方針と範囲

現行の唯一の本線はB案である。

> ユーザーの自然言語指示 → LLM推論 → 構造化JSON計画 → 検証 → 許可済み動作プリセット → ROS 2 `JointTrajectory` → Gazebo上のCRANE+ V2

- AI利用箇所は、自然言語（あいさつ・感情表現を含む）を許可済みプリセットの選択・順序・回数・制限パラメータからなるJSON計画へ変換するLLM推論である。課題要件は推論のみでも満たすため、新規学習は行わない。
- ロボット環境は、動作確認済みの講座公式Docker、ROS 2 Humble、Gazebo Sim 6、CRANE+ V2を継続利用する。
- MVP動作は次の6プリセットとする（テーマ「あいさつコミュニケーションロボット」に対応）。各動作は CRANE+ V2 の異なる関節を主役にして、可動範囲内で安全に作り、かつ見分けられるようにする（2026-10-18 Gazebo目視で確定）。
  - `bow`: お辞儀（会釈・感謝・謝罪）。肩joint2前傾。`repetitions` 可。
  - `nod`: うなずく（同意・「はい」）。肩joint2を浅く速く。`repetitions` 可。
  - `cheer`: 喜ぶ・腕を上げる（歓喜・万歳）。肘joint3跳ね上げ。`repetitions` 可。
  - `wave`: 手を振る（挨拶・「やあ」「またね」）。手首joint4左右。`repetitions` 可。
  - `rotate_base`: 左右を向く（注目・振り向く）。基部joint1旋回。`direction`（left/right）。
  - `grip`: グリッパ開閉（受け取る・呼応）。joint_hand。`repetitions` 可。
  - 旧 `look_up`（joint2後傾）は bow と同軸で見分けにくく廃止、`cheer`（joint3）と `grip` を追加した。
- 対応する入力は2層: (1) 動作名の直接指定（「お辞儀して」「3回うなずいて」）、(2) あいさつ語・感情の解釈（「こんにちは」「うれしい！」「ありがとう」「またね」）。例の複合指示: 「右を向いてからお辞儀して」「左を向いて2回手を振って」「こんにちは、それからお礼して」。
- 各プリセットの関節角、速度、所要時間、回数上限は設計ゲートでCRANE+ V2上の安全確認結果に基づき確定する（`bow` は 2026-10-13 にGazebo目視で joint2 単独 +0.4 に確定済み）。
- 教師データ収集、ACT学習、peg-in-holeは現行本線では実施しない。旧ACT一周とpeg-in-hole検証は技術検証・比較材料として `.kiro/specs/_backup/final-project-act-peg-in-hole-pre-llm/` に保存する。

## 3. 機能要件

### FR-1 自然言語入力

- 日本語の自然言語指示を1件受け付ける。
- 解釈対象は6プリセット（`bow`/`nod`/`cheer`/`wave`/`rotate_base`/`grip`）の選択、実行順序、`rotate_base` の左右、`bow`/`nod`/`cheer`/`wave`/`grip` の回数。
- 動作名の直接指定だけでなく、あいさつ語・感情表現（「こんにちは」「うれしい」「ありがとう」「またね」等）を好感度の高い動作列へ解釈する。対応表現と意図→動作の対応は設計で定義する。
- 未対応動作、曖昧で安全に解釈できない指示、危険な指示は動作計画に変換せず停止する。

### FR-2 LLMによる構造化計画

- LLMはJSON計画だけを返し、説明文やROS 2メッセージを直接生成しない。
- 計画はバージョンと順序付きアクション配列を持つ。各アクションは許可済みプリセット名と、そのプリセットで許可した制限パラメータだけを持つ。
- APIプロバイダーは未決定とする。OpenAI、Gemini等を講座サンプルとの整合、公式API仕様、料金、構造化出力、安全機能、導入負荷で比較して決定する。最新仕様は実装直前に公式ドキュメントで確認し、spec更新後に採用する。

### FR-3 計画検証と安全停止

- JSON Schema等により構文、必須項目、型、列挙値、追加プロパティ、配列長、回数、計画時間を検証する。
- 許可リスト外、不正JSON、欠落、余分な項目、過大回数、長時間計画、自由記述の関節角・速度、内部プリセットの関節可動範囲外を検出した場合は、`JointTrajectory` を送信せず停止する。
- 検証失敗理由はAPIキーや個人情報を含めず確認可能にする。

### FR-4 プリセット実行

- 検証済み計画を先頭から順に実行する。
- プリセット定義（5種）だけが関節名、目標角、速度、時間を保持し、LLM出力から生の関節値を受け取らない。
- 各プリセットをROS 2 `JointTrajectory` に変換し、Gazebo上のCRANE+ V2へ送る。
- 途中失敗、タイムアウト、ユーザー停止では後続アクションを実行しない。

### FR-5 確認可能性とフォールバック

- 実行前に、入力指示、正規化済みJSON計画、検証結果を確認できる。
- デモ当日のAPI障害に備え、以前に検証・成功した計画JSONを明示的に選んで再生できる。
- 動画とレポートでは、リアルタイムLLM推論か保存計画再生かを誤解なく明記する。保存計画再生をLLMのリアルタイム成功として扱わない。

## 4. 非機能・安全要件

- **再現性:** 同一の対象指示をリアルタイムLLM推論で3回実行し、正規化後の動作計画とGazebo上の動作順・回数が3回とも一致する。構造化出力、固定可能な推論設定、JSON正規化により揺れを抑える。
- **フェイルセーフ:** 検証完了前は一切動かさない。エラー時は後続送信を止め、安全な停止状態を維持する。
- **タイムアウト:** API応答待ちと各プリセット実行に上限を設ける。具体値はプロバイダー比較および実機相当のGazebo計測を終える設計ゲートで確定し、設定とテストに同じ値を使用する。
- **秘密管理:** APIキー、トークン、認証情報をコード、README、spec、ログ、コミットへ書かない。環境変数または `.secrets/` で管理し、`.gitignore` で除外する。キーをチャットへ貼らせない。
- **個人情報:** コード、ログ、動画、レポートに氏名、所属、メールアドレス、ローカルの個人名入り絶対パス等を含めない。
- **可観測性:** 入力、正規化計画、検証、プリセット開始・終了、停止理由を記録する。ただしプロンプト全文に秘密が含まれ得る設計にはせず、秘密をマスクする。
- **可用性判断ゲート:** 実装前にコンテナからのHTTPS接続、APIキーによる最小推論、自然言語から妥当JSONまでを検証する。着手から1〜2時間以内に通らなければB案継続を再判断し、実証済みACT系へ戻す選択肢をユーザーと協議する。

## 5. 役割分担

### ユーザー担当

- APIアカウント、APIキー、必要な課金設定を自分で用意する。キーはチャットやリポジトリへ貼らない。
- 対応動作と動作範囲を最終判断する。
- ブラウザ上のGazeboで見た目と安全性を確認する。
- Gazebo Video Recorderで最終動画を録画し、YouTubeおよびomnicampusへ提出する。
- GitHub public化を承認する。

### Kiro担当

- 講座サンプルと候補プロバイダーの公式APIを調査し、比較結果を文書化する。
- システム設計、ROS 2パッケージ、LLM呼び出し、JSON Schema、validator、安全停止、動作プリセット、`JointTrajectory`変換を実装する。
- 単体テスト、異常系テスト、E2E確認、README、レポート下地、秘密・個人情報点検、git差分を作成する。commitはユーザーが明示的に依頼した場合だけ行う。

### 共同担当

- 対応する自然言語、動作範囲、成功条件、動画構成を決定する。

## 6. 受け入れ基準

### 6.0 合格最優先の原則と線引き

本プロジェクトの目的は講座修了（合格）であり、合格を最優先する（1節）。課題条件（`course-requirements.md`）が合格に必須としているのは「AIを使う／ロボットがタスクを実行する／提出物3点（動画・コード・レポート）を出す」ことだけで、創造性・技術力等は加点要素にすぎない。

そこで受け入れ基準を2層に分ける。

- **合格必須（Must）:** 課題条件が直接求めるもの。これが揃った時点で合格ラインに到達する。省略不可。
- **加点・堅牢化（Should）:** 課題条件には無く、本作品が工夫点・堅牢化として自主的に設ける基準。合格には不要で、合格ラインに到達した後に余力で作り込む。締切が厳しい場合は縮小・省略してよい。

実装順序の原則: 合格必須（Must）を先に完成させ、提出物（AC-7）まで一度確保してから、加点（Should）に着手する。加点を理由に合格必須の提出物を後回しにしない。

### 6.1 合格必須（Must）＝合格ライン

- AC-1: 6プリセット（`bow`/`nod`/`cheer`/`wave`/`rotate_base`/`grip`）を用いた3種類以上の自然言語指示をLLMが妥当なJSON計画へ変換できる。動作名の直接指定に加え、あいさつ語・感情表現の解釈（例「こんにちは」→会釈）も含む。（課題条件: AIの使用）
- AC-2: 入力、LLMの正規化済みJSON、validator結果を実行前に確認できる。（AC-1・AC-3を成立させる最低限の運用）
- AC-3: Gazebo上のCRANE+ V2がJSONの順序、方向、回数どおりに動作する。（課題条件: ロボットがタスクを実行）
- AC-7: 1〜3分のMP4動画、public GitHub、指定項目を含むPDFレポートを準備でき、秘密・個人情報を含まない。（課題条件: 提出物3点）

**AC-1・AC-2・AC-3・AC-7 が揃った時点で合格ラインに到達する。**

### 6.2 加点・堅牢化（Should）＝余力で作り込む

課題条件には無い自主基準。合格には不要。ただし安全境界（AC-4）はB案のデータフロー上ほぼ自然に成立し、工夫点として動画・レポートに載せやすいため、優先度は加点の中で高い。設計は最初から見込んでおく（後付けできない設計事項のため）が、作り込みの深さは余力に応じて調整する。

- AC-4: 未対応・危険指示、不正JSON、許可外項目、上限超過では`JointTrajectory`を送らず停止する。（工夫点: 安全境界）
- AC-5: 同一の対象指示をリアルタイムLLM推論から3回実行し、正規化後の計画および動作結果が一致する。（堅牢化: 再現性）
- AC-6: API障害時に検証済み保存計画を再生でき、画面・動画・レポートで再生モードと明記できる。（堅牢化: フォールバック）

- プリセットごとの関節目標、速度、補間時間、回数上限、全体アクション数・計画時間上限、APIと動作のタイムアウト値。
- 自然言語入力と計画確認のUI方式（CLIを第一候補とするが未確定）。
- GitHub public化の時期。公開前に履歴を含む秘密・個人情報点検と、再配布禁止の講座・コンペ由来資産が含まれないことを確認する。

これらは `tasks.md` の設計・接続ゲートで確定し、通過前に本実装へ進まない。
